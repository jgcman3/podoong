# B3·B4 구현 및 출시 검증

작성일: 2026-10-12

## B3

커뮤니티 글·댓글·사진·반응·북마크·신고·차단과 운영자 숨김/제한, 인앱 알림 설정·조용한 시간·중복 방지·운영 작업, 매일의 질문 투표를 구현했습니다. 실제 사용자 운영 및 콘텐츠 검수는 별도 검증해야 합니다.

## B4 개발 범위

전체 기록 JSON 내보내기, 소유자 아이 삭제, 명시적 가족 소유권 이전, 관리자 연결 검증 후 계정 삭제, 접근권한 즉시 철회, 공유 기록 작성자 익명화, Storage/Auth 삭제 작업 큐 및 재시도 이력, 미등록 사진 정리, 최소 이용 이벤트 집계를 구현했습니다. 삭제/이전은 재인증과 확인 문구를 요구합니다.

집계에는 온보딩·기록 생성·할 일 완료·가족 참여·투표만 기록하며 텍스트나 아이 이름은 수집하지 않습니다. 운영자에게만 활성 가족, 둘 이상 협업 가족, 4주 유지 지표와 DB/Storage 용량을 제공합니다. 표본 부족 시 실제 측정 전 유지율을 추정하지 않습니다.

## 파일럿 통과 조건

- 30–50가족을 모집하고 동의·지원 담당자 및 운영자 계정을 지정합니다.
- 4주간 실제 사용 후 적격 코호트·활성 가족·협업·유지율을 분석합니다. 초기화한 로컬 테스트 데이터는 실제 지표로 사용하지 않습니다.
- 한국어/영어, 모바일/데스크톱, 소유자/편집자/열람자 흐름과 삭제·탈퇴·초대·날짜 변경을 점검합니다.
- 카카오·네이버·구글 각각 실제 계정 로그인·재로그인·연결·해제 및 이메일 없는 카카오 계정을 검증합니다. 현재 세 공급자 실계정 검증은 완료되지 않았습니다.
- 의료·행정 안내 콘텐츠의 담당 검수자, 출처, 검수일을 지정합니다.
- 복원 검증, 객체 백업, 사고 대응 담당자, 백업 보존기간을 확정합니다.
- 운영 대시보드의 DB/Storage 바이트를 주별 기록하고 Supabase 사용량/청구액과 트래픽·Auth 사용자 수를 함께 기록합니다. 실제 청구 비용은 자동 추정하지 않습니다.

운영 절차: [데이터 삭제·백업](../operations/data-and-backup.md).

## 원격 DB 단계적 적용 시 로그인 호환

`account_active`가 없는 원격 프로젝트에서 모든 인증 페이지가 `Account status unavailable`로 중단되는 오류를 수정했습니다. 함수 누락(`PGRST202`)일 때만 사용자 본인의 삭제 작업을 직접 조회합니다. 작업 테이블도 누락(`PGRST205`)된 B4 이전 프로젝트에서는 기존 로그인을 유지합니다. 테이블이 있으면 삭제 요청 계정을 계속 차단하며 권한·연결 오류는 통과시키지 않습니다. 이 호환 처리는 신규 테이블과 마이그레이션 적용을 대신하지 않습니다. 해당 분기 회귀 테스트 6개를 추가했습니다.

## 게시판 탐색과 투표 목록

커뮤니티는 등록한 가족 거주지역의 시·군·구 지역 게시판, 읍·면·동 동네 게시판과 같은 국가의 임신·출산·먹이기·건강·육아 일상 주제별 게시판을 제공합니다. 게시판 제목은 `강남구 게시판`·`역삼동 게시판`·`임신 게시판`처럼 표시하며 국가·지역 범위 구분은 유지합니다. 지역 범위와 국가 단위 주제 분리는 `017`에서 적용합니다. 게시판 선택 → 글 목록 → 글 상세 → 댓글 작성으로 이동하며, 목록의 글쓰기 버튼은 별도 `/community/new` 작성 화면으로 이동하고 선택한 게시판을 기본 적용합니다. 목록에서는 작성 폼을 노출하지 않습니다. 지역·주제 선택은 접힌 메뉴로 제공하며 글 수정(`/community/[id]/edit`)과 차단·신고 관리(`/community/settings`)도 별도 화면으로 분리합니다. 글과 댓글 저장에는 실제 커뮤니티 스키마가 필요합니다. 거주지역이 없으면 등록 화면으로 안내합니다. [공유 범위·DB 구조](community-home-boards.md)를 참고하십시오.

투표는 오늘의 질문과 지난 투표 목록을 구분합니다. 관리자가 등록한 실제 질문이 없을 때 오늘 질문 1개와 과거 질문 3개를 미리보기로 표시합니다. 예시 질문은 DB에 저장하거나 투표를 받지 않고 참여 수·결과를 만들어 표시하지 않습니다. 실제 질문이 등록되면 실제 데이터와 결과를 표시합니다. 운영자의 질문 등록·예약 기능은 `/ko/operations`와 `/en/operations`에서 유지합니다.

### 목록과 작성 화면 분리 검증

목록에는 작성 폼·차단 목록·신고 이력이 없으며 글쓰기 버튼을 눌러 별도 화면으로 이동합니다. 선택한 지역을 유지하고, 저장한 글은 상세 화면에서 확인합니다. 커뮤니티와 투표 브라우저 테스트를 독립된 시나리오로 나누어 각 동선을 검증합니다. 초기 통합 실행은 개발 서버 시작/화면 로딩 및 전체 제한 시간으로 중단되어 전체 통합 테스트 통과로 기록하지 않습니다.

최종 커뮤니티 브라우저 테스트 1개가 통과했습니다. 목록 → 글쓰기 → 저장 → 상세 → 댓글 동선, 사진 권한과 차단, 모바일 390px 화면의 가로 넘침 및 hydration 오류 없음을 확인했습니다. 타입 검사·ESLint·프로덕션 빌드와 단위 테스트 25개도 통과했습니다. 분리 후 전체 브라우저 테스트 6개는 재실행하지 않았습니다.

## 추가 아이 등록 오류 수정

- 문제: 가족 소유자가 다른 아이를 등록하면 `/family?error=generic`으로 돌아왔습니다.
- 원인: `src/features/family/actions.ts`의 `addChild`가 INSERT와 SELECT를 함께 요청했습니다. `child_read` 정책의 STABLE 함수 `can_read_child`는 해당 SQL 문의 스냅샷에서 새 행을 조회하지 못하므로 요청이 RLS 오류 `42501`로 거부됐습니다.
- 수정: 서버에서 아이 UUID를 생성하고 조회 없이 INSERT한 뒤 해당 아이의 오늘 화면으로 이동합니다. 기존 소유자 등록 권한과 읽기 정책을 유지하며 원격 DB 마이그레이션은 필요하지 않습니다.
- 검증: 로컬 DB에서 기존 요청 실패, 조회 없는 저장과 후속 조회 성공을 각각 확인했습니다. `tests/e2e/app.spec.ts`에 둘째 등록·새로고침·첫째 전환 테스트를 추가해 수정 전 실패, 수정 후 통과를 확인했습니다. 단위 테스트 25개·타입 검사·ESLint도 통과했습니다. 사용자 원격 DB에 테스트 데이터를 생성하지 않았습니다.
- 품질 점검: 구현 변경은 `addChild`만 대상으로 수동 검토했습니다. 기존 미커밋 작업과 겹쳐 자동 코드 정리와 브랜치 전체 리뷰는 수행하지 않았습니다. 추가 발견 사항은 없으며 수정은 로컬 미커밋 상태로 유지합니다. 원인과 로컬 수정 검증의 확신도는 높습니다.

## 다음 수유·이유식·식사 시간

2026-10-13 요청을 반영했습니다. 오늘 화면 상단의 독립 카드에 다음 수유·이유식·식사 시간을 표시하고 남은 분을 갱신합니다. 수유는 최신 모유·분유 기록의 종료 시각과 직접 정한 간격으로 계산합니다. 유축은 제외하고 진행 중인 수유는 종료 전까지 예상 시간을 만들지 않습니다. 최신 수유는 별도 조회하여 최근 기록 100개 제한의 영향을 받지 않습니다. 지난 수유 예상 시간은 지났음을 표시하며, 이유식·식사는 설정한 다음 일일 시각으로 이동합니다. 시간대와 날짜 변경·서머타임을 처리합니다.

돌봄 기록 화면의 설정 영역은 접혀 있으며 먹이기 종류를 선택해 수유 간격, 이유식·식사 각각 최대 3개 시각, 공통 시간대를 입력합니다. `child_meal_plans`에 아이별로 저장합니다. 아이 접근 권한을 가진 가족은 같은 설정을 읽고, 소유자·해당 아이의 편집자만 수정합니다. 조회자·외부 사용자·익명 쓰기는 차단합니다. 설정을 모두 비워 비활성화할 수 있고, 아이 삭제 시 함께 삭제됩니다. 설정은 데이터 내보내기에 포함되며 백업 비교 대상에도 추가했습니다. 동시 수정은 마지막 저장이 적용됩니다.

오늘 화면 안내용이며 기존 알림함 간격·조용한 시간·전달 설정은 유지합니다. 시간 설정 최초 구현에서는 이유식·식사 섭취 기록 및 자동 알림을 포함하지 않았습니다. 섭취 기록은 아래 2026-10-14 확장에서 추가했습니다. 브라우저 전용 저장은 제거했습니다.

검증: 단위 테스트 33개·DB 권한 테스트 133개·타입 검사·ESLint·프로덕션 빌드 통과. 신규 브라우저 테스트 1개에서 실제 DB 저장, 새로고침 후 유지, 가족 조회자 공유, 영문 표시, 아이별 분리, 내보내기, 390px 화면 가로 넘침·hydration 오류 없음을 확인했습니다. 전체 브라우저 테스트는 재실행하지 않았습니다. 구현 변경 파일을 대상으로 수동 검토했습니다.

원격 적용: 프로젝트 ID를 확인하고 dry-run에서 신규 `202610130009_meal_plans.sql` 한 개만 대기 중임을 확인한 뒤 적용했습니다. 읽기 전용 REST 확인에서 테이블 존재 및 익명 접근 거부(`42501`)를 확인했습니다. 원격 사용자 데이터는 생성·수정하지 않았습니다.

### 먹이기 동선 통합

후속 UI 요청에 따라 오늘 화면에서 시간 설정 폼을 제거하고 `다음 먹이기` 한 영역으로 통합했습니다. 가장 가까운 예정 시간과 나머지를 간결한 목록으로 제공합니다. 현재 배치는 상단 독립 카드이며, 마지막 수유 내부로 옮겼던 중간 변경은 아래 위치 복원 요청으로 대체됐습니다. 수유·이유식·식사는 독립 화면 대신 같은 먹이기 흐름의 종류로 선택합니다. 돌봄 기록의 `다음 먹이기 시간 설정`에서 한 종류씩 저장하며, 다른 종류의 기존 시간은 함께 보존합니다. 설정 저장 후 돌봄 기록으로 돌아옵니다. 기존 PostgreSQL 테이블·가족 권한을 유지하며 새 마이그레이션이나 원격 데이터 변경은 없습니다. 당시 후속 범위였던 이유식·식사 섭취 기록은 아래 2026-10-14 확장에서 추가했습니다.

검증: 기존 저장·공유 브라우저 테스트를 새 동선으로 갱신해 통과했습니다. 오늘 화면의 폼 제거, 기록 화면 이동, 종류별 순차 저장 후 다른 시간 유지, 조회자 설정 차단, 모바일 화면을 확인했습니다. 단위 테스트 33개·타입 검사·ESLint·프로덕션 빌드 통과. 전체 브라우저 테스트와 DB 테스트는 이번 UI 변경에서 재실행하지 않았습니다.

## 먹이기 기록 데이터 기반 확장 (2026-10-14)

오늘의 빠른 기록과 돌봄 기록에 직접 모유·분유·유축 모유 먹이기·이유식·식사를 제공합니다. 유축 자체는 기록 종류에서 유지하되 빠른 먹이기에는 노출하지 않습니다. 생산한 모유와 먹인 모유를 자동 합치지 않습니다. 기존 기록과 기존 `save_care_record` RPC는 보존합니다.

마이그레이션 `010`에서 먹이기 종류, 음식 섭취량 `amount_g`, 음식 이름 `food_name`, 입력 시간대 `record_timezone`을 추가했습니다. ml와 g를 동시에 저장하지 못하도록 DB 제약을 적용했습니다. 직접 모유 수유의 양은 새로 추정하지 않으며, 과거에 입력된 양은 자동 삭제하지 않습니다. 양 미입력은 NULL, 기존 미확인 시간대도 NULL로 보존합니다. 새 저장 RPC는 아이 권한·작성자·낙관적 버전·재전송 중복 방지·감사 이력을 유지합니다. 시간은 기존 UTC 시각과 입력 시간대를 함께 보존합니다. 수정·목록·내보내기에서 종류와 양·단위·음식 이름을 유지합니다.

마지막 수유와 수유 알림은 유축 모유 먹이기를 포함하고, 유축·이유식·식사는 수유 기록에 섞지 않습니다. 이유식·식사 서비스 진입도 같은 기록 화면으로 연결합니다. 통계 화면·집계 지표·수면 기록은 추가하지 않았습니다.

검증: DB 테스트 154개·단위 테스트 33개·타입 검사·ESLint·프로덕션 빌드 통과. 신규 먹이기 브라우저 시나리오에서 5개 빠른 기록, ml/g 구분 저장, 음식 이름·시간대, 마지막 수유, 직접 모유의 양 미추정, 내보내기, 모바일 가로 넘침 없음을 확인했습니다. 기존 수유·타이머·할 일·생일 변경 시나리오는 처음 생일 변경 표시 단계에서 실패했으나 같은 조건 재실행에서 통과했습니다. 전체 브라우저 테스트는 재실행하지 않았습니다. 구현·마이그레이션 변경 범위를 수동 검토했습니다.

### 먹이기 종류·마지막 기록·기간 입력 정리

후속 요청으로 새 먹이기 종류를 모유 수유·분유·이유식·식사 네 가지로 줄였습니다. 유축과 유축 모유 먹이기는 빠른 기록 및 신규 종류에서 제외합니다. 기존 자료·내보내기는 보존하고 기존 유축 자료는 수정·타이머 종료만 허용하며 신규 생성이나 다른 기록에서 해당 종류로 바꾸는 요청은 서버에서 거부합니다.

오늘 화면의 제목을 마지막 먹이기로 바꾸고 네 종류 중 최신 기록을 별도 조회해 보여줍니다. 음식은 g, 분유는 ml를 표시합니다. 다음 수유 예상 시간은 모유·분유 최신 기록을 별도 조회하여 이유식·식사가 수유 기준을 덮지 않습니다.

입력은 시작 시각과 먹인 시간(분)으로 바꿨습니다. 종료 시각 입력 없이 시작 + 기간으로 기존 PostgreSQL 종료 시각을 계산합니다. 자정 경계와 소수 분을 처리하며 미입력·음수·잘못된 기간에서 종료를 만들지 않습니다. 실제 0분은 명시 입력할 수 있습니다. 기존 기록에서 시작 시각을 변경하지 않으면 초·밀리초를 보존합니다. 기존 타이머 시작·종료는 유지합니다. 새 DB 마이그레이션이나 원격 사용자 자료 변환은 없습니다.

검증: 단위 테스트 41개·타입 검사·ESLint·프로덕션 빌드 통과. 브라우저 3개 시나리오에서 네 가지 선택, 종료 시각 입력 제거, 입력한 10분의 실제 DB 저장, 마지막 식사와 g 표시, 시간 설정·가족 공유, 기존 수유·타이머·할 일·생일 변경을 확인했습니다. 전체 브라우저 테스트와 DB 테스트는 재실행하지 않았습니다.
