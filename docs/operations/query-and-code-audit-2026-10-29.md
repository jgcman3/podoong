# 출시 전 코드·DB 점검

작성일: 2026-10-29 · 범위: 현재 작업 트리의 앱·운영 스크립트·최신 로컬 DB 스키마

## 판정과 적용 범위

대규모 테이블 재설계보다 조회 범위·인덱스·캐시 갱신을 먼저 개선하는 것이 타당하다. 앱 데이터가 안전하고 항상 빠르다고 보장하는 점검은 아니다. 운영 환경의 실제 부하·사진 네트워크·로그인 제공자·백업 복원은 별도로 확인해야 한다.

이번 점검에서 앱 코드와 문서는 수정했다. 마이그레이션 `059`(최근 먹인 양 인덱스), `060`(이전 운영 화면의 서비스 관리자 경계)은 **로컬에만 적용·검증하며 운영 DB에는 반영하지 않는다**. 운영은 기존 `058` 상태다. 다음 릴리스에서 스키마 변경과 앱 변경을 함께 검토한다.

## 정리한 코드

- 미사용 `feeding-select.tsx` 파일과 `UpcomingVaccinations` 컴포넌트, 해당 전용 imports 제거.
- 호출되지 않는 `isFood`, `isChildService`, `metricName`, `isFeedingKind`, 중복 `quickFeedingKinds`와 전용 타입 정리. 테스트에만 있던 죽은 helper 검사만 제거하고 실제 먹이기 입력 스키마와 시간 경계 검증은 유지.
- 이미지의 먹이기 이름은 기존 `careLabels` 재사용. 출력이 다른 시간 포맷 함수는 합치지 않음.
- 현재 지원 스키마에는 `account_active`가 있으므로 B4 이전 DB를 우회 허용하던 분기 제거. 함수가 없거나 오류면 접근을 허용하지 않으며 운영 배포 전에 마이그레이션이 준비되어야 함.
- Next route/layout/proxy·설정으로 로드되는 모듈, 복원 스크립트, 적용된 마이그레이션은 문자열 검색 결과가 적다는 이유로 삭제하지 않음.

## 조회·권한·갱신 개선

- 오늘 날짜로 타임라인을 거른 뒤 해당 기록에 필요한 사진·공개 범위만 조회. 3일 UTC 창에 들어온 이웃 날짜의 불필요한 후속 조회를 줄임. 사진·공유 메타데이터를 Map으로 구성해 기록마다 전체 배열을 반복 탐색하지 않음.
- 인사이트 선물 개요와 용돈 조회, 설정의 가족 소유권과 서비스 관리자 여부를 병렬 조회.
- 일정 저장·삭제 시 현재 달력 캐시를 무효화. 동일한 복귀 URL이 캐시돼 삭제 후 목록에 남아 보일 수 있던 경로를 수정. 할 일 및 예방접종 변경도 관련 목록 캐시를 갱신.
- 예전 `/data` 및 데이터 작업 실행 분기의 권한을 서비스 관리자 기준으로 변경. `retry_data_operation`, `operation_metrics`, 작업·이력 RLS도 같은 기준으로 제한하는 후속 SQL 작성. 일반 가족관리자·커뮤니티 운영자가 다른 계정의 삭제 작업을 읽거나 재시도하지 못하도록 DB 검증 추가.
- 기존 사진 접근권한 확인 후 ETag 검사, 비공개 Storage, 계정 삭제 확인 절차는 유지.

## 실제 인덱스·권한 확인

서울에서는 인덱스 이름·크기·사용 통계만 읽었다. 사용자 기록 내용과 실제 실행 쿼리 본문은 수집하지 않았다. 적은 운영 트래픽에서 사용 횟수가 0인 인덱스를 불필요하다고 판단하지 않았다. 유니크·외래키·중복 수면 방지·권한용 인덱스는 특히 유지해야 한다.

최신 로컬 스키마 메타데이터: RLS 미활성 public 테이블 0, 공개 Storage 버킷 0, 빈 search_path가 없는 public SECURITY DEFINER 함수 0. 이는 운영 프로젝트의 모든 설정을 원격 감사했다는 뜻은 아니다.

## 합성 자료로 측정한 쿼리

로컬 트랜잭션에 가상 보호자·아이와 **돌봄 6만 건(4종류), 분유 6만 건**을 생성했다. 로그인 역할·소유자 JWT·RLS를 적용하고 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`을 각 3회 수행했다. 종료 시 자료와 후보 인덱스를 모두 롤백했으며 잔여 가상 계정·기록·테스트 인덱스 0건을 확인했다. 아래는 로컬 warm-cache 중앙값으로, 운영 응답시간이나 사용자 체감 속도를 뜻하지 않는다.

| 대상                         | 변경 전                     | 후보 변경 후            | 결론                                                                                   |
| ---------------------------- | --------------------------- | ----------------------- | -------------------------------------------------------------------------------------- |
| 오늘 복합 OR 조건·첫 500건   | 36.725ms / 1,465 hit blocks | 36.319ms / 1,896 blocks | 날짜순 인덱스 하나로 개선되지 않음. 후보를 운영 개선안으로 채택하지 않음.              |
| 6주 인사이트·첫 500건        | 69.482ms / 5,896 blocks     | 52.707ms / 5,095 blocks | 일부 개선이나 과거 수면 겹침 조건은 여전히 넓게 탐색. 별도 쿼리 설계와 추가 실측 대상. |
| 기록이 없는 이유식의 최근 양 | 11.556ms / 1,226 blocks     | 0.033ms / 3 blocks      | 종류별 부분 인덱스 효과 확인. 필터링 60,000건 → 0건. `059`로 준비.                     |

채택한 인덱스:

```sql
create index care_latest_amount
on public.care_records(child_id,kind,started_at desc,id desc)
where amount_ml is not null;
```

재현 스크립트 `scripts/bench-care-queries.sql`은 **로컬 DB에서만** 실행한다. BEGIN/ROLLBACK과 가상 fixture를 포함하고 후보 인덱스를 영구 적용하지 않는다. 이미 적용한 최근 양 인덱스는 트랜잭션 안에서만 제거해 이전 상태를 재현하며 롤백 시 복원된다. 실제 아이 자료로 벤치마크하지 않는다.

```sh
docker exec -i supabase_db_podung psql -X -U postgres -d postgres -At < scripts/bench-care-queries.sql
```

## 추가 개선 후보

- 오늘/인사이트의 수면·활동 겹침 및 진행 중 기록 OR 조건은 자료가 많이 쌓이면 넓은 범위를 읽는다. 중복 제거·기간 겹침·시간대 의미를 유지한 분리 쿼리/RPC를 비교할 것. 단순히 기간 이전의 기록을 제외하면 밤잠과 진행 중 기록이 유실된다.
- 성장곡선은 측정 없는 일기도 평생 범위로 조회한다. 측정값과 마지막 유효 일기 날짜를 따로 가져오는 방식 검토. 빈 측정을 그냥 제외하면 기본 그래프 기간이 달라질 수 있다.
- 출생일/생후 일수 커뮤니티의 깊은 offset 페이지와 공개/차단/신고 조건은 많은 사용자·일기 자료로 별도 측정. 현재 소규모 데이터로 조인 병목을 단정하지 않음.
- 표시용 사진이 없는 기존 파일은 요청 시 원본 변환 비용이 발생한다. 운영의 준비 상태 집계와 기존 backfill 절차를 확인한 뒤 처리. 사진 바이트를 매 요청 재전송하는 것과 권한 확인 요청은 구분해야 함.

## 검증과 공개 전 남은 일

- 운영 의존성 `npm audit --omit=dev`: 알려진 취약점 0. 코드·설정 전체의 무결성을 보장하는 결과는 아님.
- 공개 준비 및 환경 분리 절차: [launch-and-release.md](launch-and-release.md).
- 운영 빌드의 전체 E2E 첫 실행은 5개 실패 후 중단했다. 과거 `/services/vaccination` 경로, 예전 계정 링크/종료 버튼 이름, 해외 주소 필수 입력 등 현재 UI와 어긋난 기대값이 포함됐다. 일정 삭제 후 캐시 갱신 누락도 발견해 수정했다. 실패 테스트를 무시하거나 전부 삭제해서 통과시킨 것으로 보고하지 않는다.

### 이번 점검의 최종 검증

- 타입 검사·린트·공백 검사 통과.
- 단위 테스트 142개, DB 테스트 665개 및 정리 검증 10개 통과.
- 수정 영향 범위의 브라우저 시나리오 12개 통과: 11개는 운영 빌드, 예방접종 1개는 마지막 경로 기대값 수정 후 개발 빌드에서 재검증.
- 운영 빌드 메뉴 재방문 테스트에서 오늘 화면 복귀 58ms·추가 RSC 조회 0회를 관측했다. 특정 로컬 실행 결과로 모든 기기/네트워크 성능을 보장하지 않는다.
- 최초 전체 실행에서 실패한 다섯 시나리오는 현재 UI 기대값과 일정 캐시를 수정한 후 각각 재통과했다. 다만 전체 72개 시나리오의 최종 완주 검증은 아직 남아 있다. 전체 E2E 통과라고 보고하지 않는다.
- 새 인덱스/운영 역할 SQL은 로컬에서만 적용했다. 서울 운영 프로젝트는 변경하지 않았다.

간소화 검토는 재사용·품질·효율·테스트 가치·주석 관점으로 수행했다. 적용은 재사용 2건(중복 배열·먹이기 이름), 품질 3묶음(미사용 모듈·컴포넌트·헬퍼/타입), 효율 3묶음(날짜별 사진 후처리 및 두 병렬 조회), 테스트 전용 코드 1묶음, 오래된 사진 설명 주석 1건이다. 포맷이 다른 시간 함수 통합과 이익이 불명확한 인덱스 추가는 제외했다. 권한·프로토콜·플랫폼 제약 설명은 유지했다.
