## 1. 목표와 계획 전제

첫 공개 출시의 목표는 부모가 아이를 등록하고, 필요한 준비를 확인하고, 돌봄 기록과 일정·할 일을 가족과 함께 관리하는 것이다. 한국 대상의 모바일 중심 반응형 웹을 한국어·영어로 제공한다. 지역·주제별 커뮤니티와 매일 투표도 첫 공개 출시 범위에 포함한다.

**확정 요구사항:** 카카오·네이버·구글 소셜 로그인 세 가지를 첫 공개 출시부터 모두 지원한다. 별도 비밀번호 생성 없이 가입·로그인하고 아이 등록이나 가족 초대 흐름으로 이어져야 한다. 제품 계획의 `AUTH-01`~`AUTH-05`를 따른다.

**오늘 화면 시간 안내(2026-10-13):** 다음 수유 예상 시간과 이유식·식사 예정 시간을 표시한다. 수유 간격과 하루 식사 시각은 아이별 Supabase DB 설정으로 저장·가족 공유한다. 오늘 화면은 다음 먹이기를 하나로 묶어 표시하며, 돌봄 기록 화면에서 종류를 선택해 시간을 설정한다. 이 동선은 구현했으며, 이유식·식사 섭취 기록은 아래 2026-10-14 기록 확장으로 추가했으며 해당 시간의 자동 알림 전달은 후속 범위다. [구현·검증 기록](../implementation/stages-b3-b4.md#다음-수유이유식식사-시간).

Supabase 사용을 확정했고 첫 세 단계 A·B1·B2의 로컬 구현을 진행했다. 실제 로그인 제공자 검증과 콘텐츠·사용성 검토가 남아 있으므로 단계 완료로 선언하지 않는다. 구현 범위·기술 결정·미완료 조건은 [구현 현황](../implementation/stages-a-b1-b2.md), 실행 방법은 [README](../../README.md)에 기록한다. 서비스별 개발·공개 일정은 아래 제안을 유지한다.

- **인력 가정:** 전담 개발자 1명, 디자인·번역·콘텐츠 검토·커뮤니티 운영 지원 별도. 개발자가 모든 역할을 맡으면 기간을 다시 산정한다.
- **기간 가정:** 첫 공개 출시까지 개발 착수 후 약 20~28주. 인터뷰 모집, 전문 검토, 운영 준비 지연은 별도 반영한다.
- **진행 기준:** 주차보다 단계별 완료 조건을 우선한다. 각 단계가 끝날 때 다음 단계의 범위와 예상 기간을 갱신한다.
- **서비스 비용:** 사용자에게 무료로 제공하는 정책과 개발·호스팅·운영 예산은 별개다.
- **후속 범위:** 직접 행정 신청·병원 예약, 개인 기관 이력 연동, 자동 번역, 해외 출시, 결제는 초기 개발에서 제외한다.

정확한 패키지 버전은 개발 환경 구성 시 호환성을 확인한 뒤 lockfile에 고정한다. 이메일은 가입의 필수 단계로 두지 않는다. 초대·안내 메일을 도입할 때 발송 서비스를 연결하고, 일정 안내 이메일과 웹 푸시는 전달 검증 후 추가한다.

### 소셜 로그인 구현 및 일정

| 제공자 | 연동 제안                                                                                                          | 준비·구현                                                                              | 검증·공개                                               |
| ------ | ------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| 카카오 | Supabase Auth 기본 Kakao 제공자 사용. [공식 문서](https://supabase.com/docs/guides/auth/social-login/auth-kakao)   | A 1~3주차에 앱 등록·동의 항목·운영 설정 준비, B1 4~6주차 구현                          | B4 17~20주차 실제 계정 검증, C 21~24주차 공개           |
| 네이버 | Supabase Custom OAuth2 제공자를 우선 검토. 네이버 응답 형식·사용자 ID 매핑·PKCE 호환성은 B1 시작에 확인            | A 1~3주차에 앱 등록·서비스 적용에 필요한 검수 준비, B1 4주차 호환성 확인, 5~6주차 구현 | B4 17~20주차 운영 설정·실제 계정 검증, C 21~24주차 공개 |
| 구글   | Supabase Auth 기본 Google 제공자 사용. [공식 문서](https://supabase.com/docs/guides/auth/social-login/auth-google) | A 1~3주차에 OAuth 앱·동의 화면·도메인 준비, B1 4~6주차 구현                            | B4 17~20주차 실제 계정 검증, C 21~24주차 공개           |

네이버 로그인은 기본 제공자 지원으로 가정하지 않는다. Supabase는 수동 endpoint 설정의 Custom OAuth2를 제공하고, 네이버는 OAuth 인증·토큰·프로필 API를 제공한다. 이 두 문서를 근거로 위 방식을 제안하지만 실제 조합의 호환성은 아직 검증되지 않았다. [Supabase Custom OAuth/OIDC](https://supabase.com/docs/guides/auth/custom-oauth-providers), [네이버 로그인 API](https://developers.naver.com/docs/login/api/api.md)

4주차에 네이버 사용자 응답 매핑과 세션·RLS 연계가 불가능한 것으로 확인되면, 세 제공자를 지원하는 인증 계층 대안과 DB 권한 연계 방식을 기술 결정 기록에 남기고 B1 기간을 재산정한다. 네이버를 제외한 채 완료로 처리하지 않는다.

- 개발·시험·운영의 callback URL과 비밀키를 분리하고 필요한 제공자 검수·동의 설정을 A부터 준비한다. 실제 외부 검수 소요 기간은 개발 주차와 별도로 관리한다.
- 제공자 사용자 ID와 내부 사용자 ID로 계정을 식별한다. 로그인 완료 후 신규 사용자의 아이 등록, 기존 사용자의 홈, 초대 확인 경로를 복원한다.
- 연결·해제는 재인증과 명시적 동의로 처리하고 마지막 로그인 수단 제거에 따른 계정 접근 상실을 방지한다. 이메일 없는 계정과 제공자별 중복 계정 처리도 B1에서 결정한다.
- OAuth state·callback 허용 경로·세션 갱신·로그아웃을 검증한다. PKCE는 제공자 호환성을 확인해 적용한다. 로그인 취소·동의 거부·제공자 장애에는 두 언어의 재시도 안내를 제공한다.

### 선택의 한계와 재검토 조건

- 관리형 서비스는 인증·저장소·예약 작업에 의존한다. SQL migration, 데이터 내보내기, 서비스 접근 모듈을 유지해 이전 비용을 줄인다.
- Vercel Hobby는 개인·비상업적 사용으로 제한되므로 서비스 운영 예산은 적합한 유료 요금제를 전제로 검토한다. 무료 서비스라고 Hobby 사용이 허용되는 것으로 판단하지 않는다. [공식 안내](https://vercel.com/docs/plans/hobby)
- DB를 서울에 두어도 인증·로그·이메일·지원 처리까지 국내에 한정된다는 뜻은 아니다. 실제 데이터 흐름과 공급자 조건은 시험 운영 전에 확인한다.
- 장시간 작업이나 외부 연동이 늘면 별도 작업 실행기를 검토한다. 모바일 네이티브 앱은 웹의 반복 사용과 기기 제약을 확인한 후 판단한다.

## 3. 아키텍처와 데이터 원칙

### 애플리케이션 구성

하나의 Next.js 앱 안에서 `family`, `care`, `calendar`, `content`, `community`, `polls` 도메인을 분리한다. 서비스는 독립적으로 이용할 수 있게 만들되 인증·아이 프로필·권한·일정·알림은 공통으로 사용한다. 운영 화면은 같은 앱의 별도 보호 경로에 둔다.

아래 디렉터리는 구현 시 도입할 제안이다.

| 경로                                      | 역할                                  |
| ----------------------------------------- | ------------------------------------- |
| `src/app/[locale]/`                       | 한국어·영어 화면과 페이지 구성        |
| `src/features/`                           | 도메인별 화면·서버 처리·검증 규칙     |
| `src/components/`, `src/lib/`             | 공통 UI, 인증, DB 접근, 날짜 유틸리티 |
| `messages/`                               | `ko.json`, `en.json` 공통 메시지      |
| `supabase/migrations/`, `supabase/tests/` | 스키마·권한 변경, DB 테스트           |
| `tests/e2e/`, `public/`                   | 브라우저 검증, 공개 브랜드 자산       |
| `docs/plans/`                             | 요구사항·로드맵·개발 계획             |

### 핵심 모델과 무결성

- `profiles`, `families`, `family_members`, `children`, `child_access`, `invitations`: 여러 아이와 보호자 관계, 아이별 접근 범위, 초대 만료·회수. 관리자·기록 가능·조회 전용 역할을 제안한다.
- `care_records`, `events`, `tasks`, `notification_preferences`, `notifications`, `job_runs`: 기록 작성자와 수정 이력, 일정 출처, 담당자, 알림 실행 상태.
- `content_items`, `content_translations`: 적용 국가·지역·유효 기간·공식 출처·검토일·검토자·번역 상태. 초안·검토·게시·보관 단계로 관리한다.
- `posts`, `comments`, `reactions`, `bookmarks`, `reports`, `blocks`, `moderation_actions`: 공개 커뮤니티와 신고 처리. 가족 기록을 자동으로 공개 게시물에 연결하지 않는다.
- `polls`, `poll_translations`, `poll_options`, `votes`: 한국어·영어가 같은 투표 ID를 사용한다. `(poll_id, user_id)` 고유 제약과 트랜잭션으로 중복·동시 참여를 처리한다.

접근은 화면·서버 검사와 DB의 행 단위 보안(RLS)을 함께 적용한다. 공개 스키마의 테이블마다 권한과 RLS를 정의하고, Storage에도 별도 접근 정책을 적용한다. 사용자 요청은 사용자 권한으로 실행하며 관리자 권한 키를 브라우저에 노출하지 않는다. [Supabase RLS 문서](https://supabase.com/docs/guides/database/postgres/row-level-security)

생일·예정일은 날짜 값으로, 기록 시각은 UTC 시각과 사용자 시간대를 기준으로 관리한다. 투표의 하루는 `Asia/Seoul` 기준이다. 출생일 등록 시 아이 ID·완료 항목·수동 일정을 유지하고, 자동 권장 일정의 변경안을 확인받는다. 알림 작업은 중복 실행 방지 키, 재시도 횟수, 실패 이력을 가진다.

## 4. 단계별 개발 로드맵

### 서비스별 개발·시험·공개 일정

아래 표는 제품 계획의 **17개 서비스 전체**에 대한 일정 제안이다. 초기 주차는 개발 착수일 기준이며, `공개 후 N개월`은 실제 첫 공개 출시일 기준이다. 후속 서비스 기간은 첫 출시 후 재산정한다. 겹치는 개발 기간은 공통 기록·일정·콘텐츠 기능을 함께 만드는 기간이며, 각각 별도 인력이 투입된다는 뜻은 아니다. 공개 시점에는 한국어·영어와 해당 서비스의 권한·삭제·운영 검증이 완료되어야 한다.

**유지 규칙:** 일정 변경 시 이 표와 아래 단계 설명을 함께 수정하고 변경 이유를 남긴다. 후속 기능은 범위와 기간을 별도로 정할 때까지 예정으로 유지하며, 첫 공개 출시 필수 소셜 로그인과 커뮤니티·투표를 임의로 후속 일정으로 옮기지 않는다.

### A. 범위·디자인 검증 — 1~3주차

**할 일:** 첫 출시 기능과 지원 지역·콘텐츠 목록을 확정한다. 세 소셜 제공자의 앱 등록·운영 설정·검수 준비를 시작한다. 로그인·오늘·기록·일정·전체 서비스·커뮤니티의 모바일 화면을 설계하고 영어 화면도 함께 검토한다. 소셜 로그인 → 아이 등록 → 첫 기록 → 할 일 완료 → 가족 초대 → 투표 결과 흐름을 시안으로 검증한다.

**산출물:** 화면 설계, 디자인 토큰, 권한 표, 콘텐츠 운영 절차, 기술 결정 기록. 제품 계획의 제안에 따라 인터뷰 10~15명을 모집한다.

**완료 조건:** 주요 사용자 유형이 두 언어에서 핵심 흐름을 수행하며, 발견된 사용성 문제에 수정 방안이 있다. 개발 범위와 콘텐츠·운영 담당자가 정해져 있다.

### B1. 개발 기반·가족 프로필 — 4~6주차

**의존성:** A의 화면·권한·기술 선택 확정.

**할 일:** 개발·시험·운영 환경 분리, CI, DB migration, 공통 UI·다국어, 카카오·네이버·구글 가입·로그인·로그아웃·계정 연결, 가족·아이 등록, 보호자 초대·권한 회수, 감사 이력을 구축한다. 4주차에 네이버 연동 호환성을 확인한다. 실제 데이터는 운영 환경에만 둔다.

**완료 조건:** 다른 가족·허용되지 않은 아이의 조회와 수정이 DB·서버 모두에서 차단된다. 만료·재사용·회수된 초대를 거부하고, 두 보호자가 서로 다른 언어로 같은 아이를 관리할 수 있다.

세 소셜 제공자에서 신규 가입·재로그인·세션 갱신·로그아웃을 확인하고, 로그인 후 아이 등록·홈·초대 경로가 복원되어야 한다. 설정 중이거나 버튼만 있는 제공자는 구현 완료로 세지 않는다.

### B2. 기록·오늘·일정·콘텐츠 — 7~11주차

**의존성:** B1의 권한 모델과 프로필 안정화.

**할 일:** 수유·분유·유축 기록과 타이머·수정, 마지막 기록 표시, 오늘 할 일 최대 3개와 전체 목록, 담당자·완료·미루기, 병원 일정·메모를 구현한다. 임신·출산 준비·출생 행정·산후 기본 목록·핵심 지원 안내를 검토된 콘텐츠로 제공한다. 모든 서비스 목록에는 제공 상태를 표시한다.

**완료 조건:** 새로고침·중복 저장에서도 기록이 중복되지 않는다. 타이머는 저장된 시작 시각으로 복원한다. 출생일 전환과 예정일 수정 시 완료·수동 일정이 보존된다. 공식 링크 방문을 신청 완료로 처리하지 않는다. 두 언어의 핵심 안내·오류·빈 화면이 준비된다.

### B3. 알림·커뮤니티·투표·운영 기능 — 12~16주차

**의존성:** B2의 일정·콘텐츠 구조, 신고 운영 기준.

**할 일:** 앱 내 알림함, 조용한 시간·종류·빈도·미루기, 실패 작업 재처리를 만든다. 지역·주제별 글·댓글·사진·공감·저장·신고·차단과 운영자의 숨김·이용 제한·공지 기능을 구축한다. 하루 한 질문의 예약 게시, 계정당 한 표, 마감 전 변경, 미참여 결과 열람, 지난 투표를 구현한다.

**완료 조건:** 완료한 일과 회수된 권한에 대한 알림을 중단한다. 투표 마감 경계·동시 요청에서도 한 표 제약을 유지하며, 마감 후 변경을 거부한다. 숨긴 게시물과 차단 정책이 피드·직접 링크·첨부 접근에 일관되게 적용된다. 신고 처리 이력이 남는다.

**범위 조절:** 웹 푸시와 외부 일정표 연결은 기기별 검증 이후로 미룰 수 있다. 지역·시기별 투표 집계는 소규모 집계 기준을 정하기 전에는 공개하지 않는다.

### B4. 비공개 시험 운영 — 17~20주차

**의존성:** B1~B3 통합, 콘텐츠·번역 검토, 운영 담당자 확보.

**할 일:** 제품 계획의 제안에 따라 30~50가족으로 시험한다. 기록 내보내기, 계정·아이 삭제, 첨부 정리, 권한 회수, 백업 복구, 장애 대응을 검증한다. 핵심 행동과 4주 반복 사용, 가족 협업, 알림 불편, 비용을 측정한다.

**완료 조건:** 데이터 유실·권한 우회·핵심 흐름 중단 문제가 해결되어 있다. 삭제와 복구 결과를 확인했고 운영자가 신고·문의·실패 알림을 처리할 수 있다. 실패한 검증에는 수정과 재검증 기록이 있다.

### C. 첫 공개 출시 — 21~24주차, 보완 여유 최대 4주

**의존성:** 비공개 시험 운영 통과, 공개 운영 준비 완료.

**할 일:** 모바일·데스크톱과 한국어·영어를 최종 검증하고 제한된 모집부터 공개 범위를 늘린다. 이용·개인정보 안내, 콘텐츠 출처, 문의 창구, 장애·롤백 절차를 준비한다. 오류·작업 실패·지출 알림을 설정한다.

**완료 조건:** 아래 출시 체크리스트를 모두 충족한다. 커뮤니티 운영이 준비되지 않으면 첫 공개 출시 범위를 다시 결정하며, 자동으로 기능을 제외해 출시하지 않는다.

### D. 돌봄 기록 확장 — 공개 후 1~3개월, 재산정

**예방접종·독감 추가 구현(2026-10-14):** 공식 안내, 아이별 접종 예정·완료 목록과 별도 작성·상세·수정 화면, 백신·차수·독감 절기·예정일·실제 접종일·병원·메모를 제공한다. 오늘·일정 화면에 예정 접종을 연결하고 가족 권한·내보내기·삭제를 적용한다. 공식 접종 이력 자동 연동, 개인별 접종 일정 자동 생성과 예약 대행은 후속 범위다. [구현 문서](../implementation/stage-d-vaccination.md)를 참고한다.

**2026-10-14 구현 현황:** 사용자 요청으로 수면·기저귀·배변·성장·발달 기록을 앞당겨 구현했다. 목록 → 작성 → 상세 → 수정·삭제 화면을 분리하고 가족별 아이 접근 권한, 한국어·영어, JSON 내보내기와 삭제를 연결했다. 수면은 낮잠·밤잠·진행 중 타이머와 중복 검사, 기저귀는 종류·대변 상태·메모·오늘 기록 수, 성장은 신체 측정·발달 일기·비공개 사진을 제공한다. 오늘 화면의 빠른 돌봄 기록에서 각 서비스의 작성 화면으로 이동한다. 통계 그래프·성장 백분위·의학적 판단은 추가하지 않는다. 실제 가족 반복 사용 검증은 남아 있다. 자세한 내용은 [D 구현 현황](../implementation/stage-d-child-care.md)을 참고한다.

수면·기저귀 → 이유식 기본 기록 → 성장·발달 → 예방접종 안내 순으로 수요를 확인하며 추가한다. 단계마다 기록 편의·가족 공유·두 언어·내보내기·삭제를 검증한다. 음식 반응과 진단된 알레르기는 구분하고 건강 콘텐츠는 검토 후 게시한다.

**완료 조건:** 각 추가 서비스가 기존 홈·일정과 연결되고 실제 반복 사용을 확인한다. 통계 화면이 진단·발달 순위·복용량 처방으로 해석되지 않도록 검토한다.

### E. 기관·지역 확장 — 공개 후 4~6개월 목표, D 이후 재산정

어린이집·유치원·취학 준비의 관심 기관, 준비 서류, 모집·입소 일정을 추가한다. 지역별 안내를 늘리고 공개 기관 데이터의 사용 조건·갱신 주기·실패 시 공식 링크 대체 경로를 정한다. 직접 신청과 개인 이력은 별도 연동 허가와 운영 검증을 거친다.

**완료 조건:** 확장 지역마다 출처와 갱신 담당자가 있고, 사용자 입력 상태와 기관 확인 상태를 구분한다.

### F. 국가·언어 확장 및 수익화 — 시점 미정

기존 서비스의 유지·운영 비용·콘텐츠 관리가 안정된 후 검토한다. 새 국가는 제도·건강 안내·기관 정보·단위·시간대·운영 인력을 준비한다. 충분한 사용자 확보의 기준을 먼저 정하고, 유료화는 별도 제품 결정으로 진행한다.

## 7. 성과 측정과 다음 착수 항목

비공개 시험에서 등록 후 첫 기록·할 일 완료, 첫 행동까지의 시간, 4주 가족 유지, 두 보호자 이상 협업, 알림 끄기·중복, 투표 참여·결과 열람, 영어 흐름 성공, 문의·신고 처리 시간, 가족당 비용의 기준값을 구한다. 이후 단계별 목표치를 정하며 가입자 수만으로 확장을 판단하지 않는다.

개발 착수 전에 다음 순서로 준비한다.

1. 개발 인력·주당 투입 시간·운영 지원과 예산을 확정하고 예상 기간을 갱신한다.
2. 첫 출시 기능·지원 지역·검토할 콘텐츠를 목록으로 고정한다.
3. 권한 표와 날짜 전환·삭제·보관 정책을 정의한다.
4. A의 핵심 화면을 설계하고 한국어·영어 사용성 검증을 진행한다.
5. 기술 결정 기록과 B1의 상세 구현 계획을 작성한 뒤 개발 환경을 구성한다.

## 먹이기 기록 기반 확장 (2026-10-14)

오늘의 빠른 기록과 새 돌봄 기록은 모유 수유·분유·이유식 세 종류이며 유축·유축 모유·식사는 제거한다. PostgreSQL에 섭취 종류·실제 양(ml 또는 g)·음식 이름·시작과 종료·입력 시간대를 보존한다. 양을 모르는 경우는 NULL로 유지한다. 직접 모유는 시간으로 기록하며, 시작 시각과 먹인 시간(분)을 입력해 종료 시각을 계산한다. 마지막 먹이기는 이유식도 포함해 선택한다. 이전 유축·유축 모유·식사 자료와 식사 시간 설정은 사용자 요청으로 삭제한다. 기존 기록은 변환하지 않는다. 기본 저장·편집·권한·내보내기를 검증하며, 통계 화면·그래프와 수면 기록은 이번 구현에 포함하지 않는다.

### 먹이기 입력 편의 개선 — 2026-10-14

타이핑 부담을 줄이기 위해 먹인 시간과 분유·이유식 양을 선택형으로 변경한다. 시간은 5·10·15·20·30·45·60분 버튼으로, 분유는 10~600ml(10ml 간격), 이유식은 5~500g(5g 간격)을 제공한다. 선택값은 섭취 권장량이 아니라 기록 편의를 위한 입력 후보이며 실제 먹인 값을 선택한다. 모유는 기존처럼 시간으로 기록하고, 모르는 양은 NULL로 남긴다. 음식 이름 입력칸은 제거한다. 기존 기록의 비정형 시간·양과 음식 이름은 보존하고 타이머의 실제 측정 시간도 유지한다.

### 일정·할 일과 오늘 화면 정리 — 2026-10-14

사용자 요청으로 월간 달력뷰를 제거하고 일정·할 일 목록과 페이지 이동으로 되돌린다. 날짜 없는 할 일도 목록에 유지한다. 오늘 화면의 ‘오늘·내일·N일 후’ 표시는 유지한다. 별도 최근 돌봄 영역 대신 빠른 돌봄 기록에서 모유·분유·이유식·수면·기저귀·배변·성장·발달을 6개 카드로 제공한다. 수면, 기저귀·배변, 성장·발달은 각각 하나의 서비스로 묶는다. 조회 전용 보호자는 작성 화면 대신 기록 목록으로 이동한다. 저장된 기록과 기존 관리 기능은 보존한다.

### 가족 거주지역 기반 — 2026-10-15

향후 동네별 부모 커뮤니티를 위해 우선 한국의 시·도 → 시·군·구 → 읍·면·동을 드롭다운으로 선택한다. 공식 법정동 목록의 국가 코드 `KR`와 10자리 지역 코드를 PostgreSQL에 저장해 동명이인 지역을 구분한다. 행정동 기준이 아닌 법정동 기준이며 리·상세 주소·좌표는 수집하지 않는다. 기존 직접 입력 자료의 이전은 필요하지 않다.

우리 가족에서 등록·변경·삭제하며 같은 가족의 모든 아이가 공통 사용한다. 소유자만 수정하고 다른 가족 구성원은 조회한다. 상위 지역 변경 시 하위 선택을 초기화한다. 후속 서비스는 `context.family`의 국가·지역 코드를 사용한다. 동네 커뮤니티 연결은 아래 `017` 단계에서 구현한다. 행정구역 개편 시 연결 이전 정책과 해외 국가·지역 선택은 후속 단계다. [구현·자료 갱신 안내](../implementation/family-residence.md).

#### 해외 확장 대비 DB 구조 — 2026-10-15

현재 화면에는 국가 선택을 추가하지 않고 한국만 제공한다. DB는 국가 목록과 지역 목록을 분리하며, 국가+지역 코드 복합 키와 부모·깊이·종류로 국가마다 다른 행정구역 단계를 담는다. 한국의 숫자 10자리 형식을 전 세계 공통 제약으로 사용하지 않는다. 가족은 국가와 지역 키를 참조하며 커뮤니티도 같은 키를 기준으로 연결한다. 신규 국가는 기본 비활성으로 등록하고, 지역 자료·국가별 입력 검증·화면 준비를 마친 후 활성화한다. `016`으로 구조를 준비하며 국가 추가만으로 새 컬럼이나 국가별 전용 테이블을 만들지 않는다. 해외 자료와 국가 선택 UI 구현은 추후 진행한다.

### 거주지역 기반 부모 게시판 — 2026-10-15

같은 시·군·구의 지역 게시판과 같은 읍·면·동의 동네 게시판을 분리한다. 주제별은 국가 단위로 함께 이용한다. 가족에 등록한 거주지역으로 자동 연결하며 게시판 제목은 `강남구 게시판`, `역삼동 게시판`, `임신 게시판`처럼 마지막 지역명 또는 주제로 짧게 표시한다. 국가·전체 지역 코드는 내부 구분에 유지한다. 목록과 별도 작성 화면의 기존 동선을 유지하고 지역 타이핑은 제거한다. 지역이 없으면 가족 거주지역 등록을 안내한다.

`017`은 국가·범위·지역·주제로 식별하는 게시판과 글의 연결, 지역 계층의 커뮤니티 역할을 추가한다. 읽기·댓글·사진에도 같은 소속 범위를 적용하며 운영자의 신고 처리 권한은 유지한다. 수정·이사로 기존 대화의 게시판이 이동하지 않게 한다. 다른 국가를 추가하면 국가별 주제 게시판도 분리한다. `018`에서 작성 화면을 열어둔 사이 주소가 바뀐 경우 새 지역에 자동 게시하지 않고 재확인을 요청한다. [상세 설계·검증](../implementation/community-home-boards.md).

### 3초 육아 기록 UX — 2026-10-25

오늘 화면의 모유·분유·이유식·수면·기저귀를 직접 기록하고 최근 기록을 타임라인으로 모은다. 모바일은 큰 버튼과 양 눈금·하단 시트, 데스크톱은 목록 옆 입력 패널로 구성하며 화면 크기 변경 중에도 입력값을 유지한다. 진행 중인 수유·수면을 같은 화면에서 종료한다. 메모·시간은 펼쳐 입력하며 성장·발달과 추가 항목은 기존 상세 기록으로 연결한다. 다음 먹이기 독립 카드를 유지하고 통계·그래프는 추가하지 않는다. 기존 PostgreSQL 테이블과 RLS·저장 RPC를 재사용하며 실제 시간·단위·미상 양과 수정 버전을 보존한다. [구현·검증](../implementation/quick-care-experience.md).

### 빠른 기록 확장과 날짜별 섭취량 — 2026-10-25

빠른 기록을 모유·분유·이유식·기저귀·배변·수면·목욕·병원·체온·투약·간식·놀이·터미타임 13종으로 확장했다. 밝은 기본 테마에서 색상 아이콘과 가로 드래그로 선택하고, 설명 문구를 줄인다. 목록 제목은 날짜(요일), 오른쪽은 해당 날짜의 `총 ml (분유양 + 이유식양)`으로 표시한다. 새 이유식은 ml로 저장하며 이전 g 기록은 환산 없이 보존하고 ml 합계에서 제외한다. 직접 모유·진행 중·양 미상 기록은 총 ml로 환산하지 않는다. 기존 통계·그래프의 후속 구현 방침은 유지한다. [상세 구현](../implementation/quick-care-experience.md).

### 과거 날짜 탐색과 최근 돌봄 요약 — 2026-10-26

오늘 화면의 기록 영역에서 스크롤바 없는 좌우 드래그·스와이프로 날짜를 바꾼다. 날짜별 자료는 가족 접근 권한으로 조회하고 요일·섭취량도 함께 갱신한다. 화살표·키보드·오늘 복귀를 지원하며 미래 날짜는 막는다. 진행 중인 돌봄은 별도로 유지한다. 상단의 아이 이름 제목·보호자 초대·다음 먹이기 카드는 제거하고 마지막 기저귀·식사·수면의 경과 시간을 표시한다. 마지막 식사는 모유·분유·이유식을 모두 포함한다. 기존 시간 설정 자료는 보존한다.

### 통합 일정과 빠른 등록 — 2026-10-26

오늘 기능 목록에 예방접종을 추가한다. 일정과 할 일 상단의 병원·예방접종·투약·할 일 버튼에서 선택한 등록 화면만 연다. 병원 방문·투약 예정은 날짜·선택적 시각·입력 시간대를 저장하며, 실제 돌봄 기록과 구분한다. 기존 예방접종과 일반 일정을 권한이 적용되는 뷰로 함께 조회해 수정·완료·삭제를 즉시 반영한다. 오늘의 다가오는 일정에도 함께 표시하고 별도 예방접종 카드는 중복되지 않게 제거한다. [상세 구현·검증](../implementation/calendar-care.md).

### 오늘 할 일 정리 — 2026-10-26

오늘 화면에 ‘오늘 할 일’과 간단한 추가 창을 제공한다. 제목·날짜만으로 일반 할 일을 저장하며, 카드의 오른쪽 상태 배지·체크 버튼은 제거한다. 기존 일정 메뉴의 상세 편집·완료 처리는 유지하고, 일반 할 일 분류를 저장 함수의 허용 목록에 추가한다.

### 오늘 카드 표시 조건과 왼쪽 체크박스 — 2026-10-26

오늘 화면은 오늘 날짜의 할 일·예정 일정이 있을 때만 해당 카드를 표시한다. 미지정·과거·미래 날짜는 오늘 카드에 포함하지 않는다. 할 일은 왼쪽 체크박스로 완료·해제하며, 오른쪽 상태·체크 표시는 제거한다. 오늘 추가·전체 보기 링크는 없애고 등록을 일정 메뉴로 모은다. 일정 메뉴의 페이지 제목은 숨기고 ‘해야 할 일’로 목록 이름을 바꾸며, 상단에 일반 일정 아이콘을 추가하고 목록 안의 일정 추가 버튼은 제거한다.

### 월간 일정과 하단 시트·스와이프 — 2026-10-26

최신 요청에 따라 일정에 월간 달력을 다시 도입한다. 이전·다음 달과 날짜 선택으로 일반 일정·병원·투약·예방접종을 확인하며, 선택 날짜의 목록을 표시한다. 추가·수정은 PC와 모바일 모두 하단 시트에서 처리한다. 일정 메뉴의 할 일 체크박스는 제거하고 할 일·일정 모두 오른쪽 밀기로 수정, 왼쪽 밀기로 삭제 버튼을 연다. 삭제 확인과 키보드용 더보기 메뉴를 제공한다. 할 일 상태는 수정 시트에서 바꾸고 오늘 화면의 왼쪽 체크박스는 유지한다. 원래 PostgreSQL 자료·권한·접종 버전 검사를 재사용한다. [상세 구현](../implementation/calendar-care.md).

### 선택 날짜의 할 일과 전체 스와이프 — 2026-10-26

달력 아래 반복 날짜 제목과 일정·할 일 카드의 점점점 메뉴를 제거하고 여백을 줄인다. 할 일도 달력의 날짜 선택과 표식에 연결하며, 선택한 날짜의 자료만 보여준다. 일정과 할 일 모두 끝까지 오른쪽으로 밀어 놓으면 수정 시트가 열리고, 왼쪽으로 밀어 놓으면 바로 삭제한다. 짧게 밀기는 작업 버튼만 표시하며 키보드 포커스로도 접근할 수 있다. 월간 조회는 100건 목록 제한을 적용하지 않는다. [구현·검증](../implementation/calendar-care.md).

### 할 일 제목 제거와 완료 체크박스 — 2026-10-26

일정 메뉴의 ‘해야 할 일’ 영역 제목을 제거하고 목록 항목 왼쪽에 완료·해제 체크박스를 추가한다. 날짜별 목록과 좌우 드래그 수정·삭제를 함께 제공한다. 체크박스 성공 시 선택 날짜·스크롤을 유지하고 오늘 화면에도 상태를 반영하며, 조회 전용 가족은 체크박스를 사용할 수 없다. [구현·검증](../implementation/calendar-care.md).

### 캘린더와 날짜별 목록 연결 — 2026-10-26

캘린더와 선택 날짜의 일정·할 일을 하나의 카드로 통합한다. 공통 날짜 제목과 선택 칸의 강조색을 맞추고 ‘일정’·‘할 일’ 소제목으로 구분한다. PC는 나란히, 모바일은 캘린더 아래로 배치하며 날짜 전환 시 제목과 두 목록을 함께 갱신한다. [구현·검증](../implementation/calendar-care.md).

### 오늘 기록 날짜에 할 일·일정 연결 — 2026-10-26

오늘 화면의 날짜별 기록 카드에 할 일·일정을 함께 배치한다. 이전 날짜를 선택하면 그날의 기록·섭취량·할 일·예정 일정으로 함께 바뀌며, 날짜별 자료가 있는 하위 영역만 표시한다. 과거 할 일의 완료·해제를 저장하고 선택 날짜를 유지하며 조회 전용 권한을 적용한다. [구현·검증](../implementation/calendar-care.md#오늘-기록-날짜와-할-일일정-통합--2026-10-26).

### 휴대폰 하단 기능 선택 — 2026-10-26

오늘·일정 메뉴는 화면 폭 760px 이하에서 기능 버튼을 하단 주 메뉴 위에 고정한다. 오늘의 14종은 가로 스크롤로 선택하고 일정의 5종도 같은 위치에서 누른다. 본문·안전 영역 여백을 확보하고 입력 시트가 열리면 기능 바를 숨긴다. PC로 창을 넓히면 원래 배치로 돌아가며 입력 상태는 유지한다. [구현](../implementation/quick-care-experience.md#휴대폰-하단-기능-바--2026-10-26).

### 네 메뉴의 상단 아이 선택 통일 — 2026-10-26

오늘·일정과 할 일·우리 가족·전체 서비스에 아이 이름·나이 선택 영역, 언어 전환, 계정 버튼을 같은 위치로 통일한다. 본문의 반복 아이 정보·아이 선택 버튼은 제거한다. 상단에서 아이를 바꿔도 현재 메뉴와 일정의 선택 월·날짜를 유지한다. [구현](../implementation/quick-care-experience.md#하단-네-메뉴의-공통-상단--2026-10-26).

### 주간 인사이트·패턴·OpenAI 브리핑 — 2026-10-26

최신 요청으로 기존 통계 보류 결정을 변경하고 주간 인사이트를 구현한다. 하단 메뉴는 오늘·일정과 할 일·인사이트·우리 가족·전체 서비스 다섯 개이며 공통 상단의 아이·언어 선택을 유지한다. 16개 돌봄 기능의 주간 주요 수치·일별 그래프·시간대 패턴을 기존 PostgreSQL 기록으로 집계한다. 양·시간·횟수·측정값의 단위를 구분하고 진행 중·미입력·날짜 경계를 처리한다. OpenAI 키가 없으면 명시적인 예시 브리핑을, 키가 설정되면 권한 확인 후 집계 수치 기반의 실제 브리핑을 생성한다. [집계 규칙·설정·검증](../implementation/insights.md).
