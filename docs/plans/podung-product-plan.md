# 포둥 제품 및 서비스 계획

작성일: 2026-10-12  
버전: 0.4
갱신: 2026-10-29
프로젝트: 포둥 · podoong

포둥은 출산 예정일과 아이의 생일을 바탕으로, 임신부터 초등학교 입학 전까지 필요한 돌봄 기록과 준비할 일을 함께 관리하는 웹 플랫폼이다. 개별 서비스는 독립적으로 사용할 수 있으며, 부모는 하나의 홈과 일정에서 가족의 상황을 확인한다. 초기에는 한국에 거주하는 가족을 대상으로 한국어와 영어를 함께 제공하고, 충분한 사용자를 확보하기 전까지 무료로 운영한다.

출시 단계, 세부 화면 구성, 운영 방식과 검증 기준은 아래 제안을 바탕으로 개발 준비 과정에서 확정한다. 기술 스택과 개발 일정은 아직 정하지 않았다.

서비스별 개발·시험·공개 일정과 기술 스택 제안은 [개발 및 출시 로드맵](podung-roadmap.md)에 정리한다. 제품 범위와 확정 요구사항은 이 문서, 일정과 구현 순서는 로드맵을 기준으로 함께 관리한다.

### 가입·로그인 필수 요구사항

2026-10-12 추가 확정 사항이다. 아래 요구사항은 기술 선택이나 일정 조정 과정에서 누락하거나 후속 출시로 미루지 않는다.

- **AUTH-01:** 첫 공개 출시에서 카카오·네이버·구글 로그인 버튼을 모두 제공한다. 같은 소셜 로그인 흐름에서 신규 가입과 재로그인을 처리하며 별도 비밀번호 생성을 요구하지 않는다.
- **AUTH-02:** 처음 가입한 사용자는 필요한 동의 후 예정일 또는 생일 등록으로 이어진다. 기존 사용자는 홈으로, 초대 링크로 방문한 사용자는 로그인 후 해당 초대 확인으로 돌아간다.
- **AUTH-03:** 휴대폰 번호·주소 등 불필요한 추가 정보를 가입 단계에서 요구하지 않는다. 제공자가 이메일을 반환하지 않는 경우의 처리도 정의해 불필요한 가입 장벽을 줄인다.
- **AUTH-04:** 계정 연결은 본인 확인 후 명시적으로 처리한다. 이메일이 같다는 이유만으로 서로 다른 소셜 계정을 무조건 병합하지 않으며, 연결 후 가족·아이 데이터와 권한을 유지한다.
- **AUTH-05:** 로그인 취소·동의 거부·연동 실패·세션 만료 시 한국어·영어 안내와 재시도 경로를 제공한다. 로그아웃·탈퇴 및 소셜 연결 해제 처리 범위를 정의한다.

세 제공자의 실제 운영 로그인과 신규·기존 사용자 흐름을 검증해야 공개 출시가 완료된다. 특정 제공자의 설정·심사·연동이 지연되면 의존성과 출시 영향을 명시해 일정을 재검토한다.

## 2. 해결할 문제와 핵심 가치

부모는 수유를 기록하는 곳, 병원 일정을 확인하는 곳, 지원금을 찾는 곳, 어린이집을 알아보는 곳을 각각 찾아야 한다. 정보를 찾았어도 언제 실행해야 하는지, 어떤 준비물이 필요한지, 가족 중 누가 처리했는지 확인하기 어렵다.

포둥은 아이의 시기와 가족의 상황에 맞춰 ‘지금 해야 할 일’을 보여주고, 기록과 준비, 실행, 완료 확인을 연결한다. 예를 들어 출산 후 필요한 행정 절차를 확인하고, 준비물을 점검하고, 공식 신청 페이지로 이동한 다음, 부모가 신청 상태를 기록할 수 있다.

첫 방문에서 많은 정보를 요구하지 않는다. 출산 예정일이나 생일로 시작하고, 지원금 안내에 지역이 필요하거나 가족 공유를 원하는 시점에 추가 정보를 받는다.

실제 출생일을 등록하면 같은 아이의 프로필을 유지하면서 예정일 기반 일정을 출생일 기준으로 전환한다. 기존에 완료한 일과 부모가 직접 정한 일정은 보존하고, 변경되는 권장 일정은 부모가 확인할 수 있게 한다.

생일만으로 모든 일을 자동 결정하지 않는다. 지역, 이미 완료한 일, 기관 이용 여부, 보호자가 정한 계획과 공식 안내를 함께 반영한다. 건강·발달 안내는 개인차를 고려하고 아이를 순위로 비교하지 않는다.

**먹이기 기록 요구사항(2026-10-14):** 돌봄 기록은 직접 모유 수유·분유·이유식을 포함하며 오늘의 빠른 기록에도 제공한다. 직접 모유 수유의 시간과 병수유 섭취량(ml), 이유식 섭취량(g)을 구분한다. 후속 요청에 따라 유축·유축 모유 먹이기·식사를 제거하고 기존 해당 기록과 식사 시간 설정도 삭제한다. 양을 모르면 미입력으로 유지하며 기존 기록을 자동 변환하지 않는다. 입력은 시작 시각과 먹인 시간(분)으로 하고 종료 시각을 자동 계산해 종류·양·단위·음식 이름·시각·기록 시간대를 보존한다. 오늘의 마지막 먹이기는 세 종류 중 가장 최근 것을 표시한다. 통계 화면 구현은 추후 진행한다.

## 6. 화면 구성과 핵심 이용 흐름

### 주요 메뉴

모바일의 기본 메뉴는 ‘오늘’, ‘기록’, ‘일정’, ‘커뮤니티’, ‘전체 서비스’를 제안한다. 아이 전환과 가족 설정은 공통 영역에서 접근한다. 데스크톱에서는 같은 구조를 넓은 화면에 맞춰 배치한다.

### 오늘 화면

- 선택한 아이와 임신 주차 또는 나이, 현재 시기.
- 우선순위가 높은 오늘 할 일 최대 3개와 전체 목록으로 가는 버튼.
- 자주 쓰는 기록 버튼과 마지막 돌봄 기록, 기록한 보호자.
- 이번 주 일정과 기한이 다가오는 준비 항목.
- 오늘의 투표와 관심 지역·주제의 커뮤니티 글.

요약 화면에 보이지 않는 할 일도 전체 목록에서 찾을 수 있어야 한다. 기한이 임박한 항목은 눈에 띄게 표시하고, 긴급성이 낮은 제안은 뒤로 미룰 수 있다.

### 대표 흐름

1. **처음 시작:** 언어 선택 → 카카오·네이버·구글 중 소셜 로그인 → 필요한 동의 → 예정일 또는 생일 등록 → 현재 시기의 홈 확인 → 첫 기록이나 할 일 완료.
2. **가족 공유:** 보호자 초대 → 공유 범위 확인 → 같은 기록 확인 → 할 일 담당자 지정과 인계 메모.
3. **외부 신청:** 대상 조건 확인 → 준비 서류 확인 → 공식 페이지 이동 → 사용자가 신청 상태 기록 → 후속 일정 확인.
4. **커뮤니티:** 관심 지역·주제 선택 → 글과 댓글 확인 → 질문 작성 또는 오늘의 투표 참여 → 결과 확인.

공식 사이트를 방문한 사실과 신청이 완료된 사실은 구분한다. 외부 시스템이 확인해 준 상태인지, 보호자가 직접 입력한 상태인지도 표시한다.

## 7. 디자인과 사용성

포둥의 화면은 크림색 바탕과 복숭아색 계열을 중심으로 구성하고, 민트색을 보조색으로 사용한다. 둥지와 작은 동물 캐릭터는 환영, 빈 화면, 완료 화면에 활용한다. 일정과 기록 화면에서는 읽기 쉬운 글자와 빠른 조작을 우선한다.

| 요소         | 디자인 제안                                           |
| ------------ | ----------------------------------------------------- |
| 배경         | 따뜻한 크림색 `#FFFAF5`                               |
| 주요 면 색상 | 부드러운 복숭아색 `#F9E4D5`                           |
| 기본 글자    | 짙은 갈색 `#403A36`                                   |
| 주요 버튼    | 갈색 계열 `#88573F`                                   |
| 보조색       | 연한 민트색 `#E3EFE5`                                 |
| 형태         | 둥근 카드, 여유 있는 간격, 간결한 아이콘              |
| 캐릭터       | 둥지 안의 작은 동물. 최종 캐릭터와 로고는 별도 디자인 |

색상은 초안이며 실제 화면에서 대비와 가독성을 검증한다. 상태를 색상만으로 전달하지 않고 글자와 아이콘을 함께 사용한다.

- 한 손으로 자주 쓰는 기록을 남길 수 있는 충분한 크기의 버튼.
- 잘못 입력한 기록을 쉽게 수정하거나 되돌리는 동작.
- 밤중 돌봄에 맞춘 어두운 화면과 움직임 줄이기 설정.
- 키보드 조작, 화면 읽기 도구, 확대 화면에서도 사용 가능한 구조.
- 영어의 긴 문장에도 버튼과 카드가 깨지지 않는 배치.
- 기록을 놓쳤다고 죄책감을 주지 않는 문구와 알림.

## 8. 알림과 할 일

알림은 일정, 마감, 부모가 설정한 돌봄 계획, 공식 안내의 변경을 바탕으로 제공한다. 각 알림에는 대상 아이, 이유, 날짜, 다음 행동을 표시한다.

사용자는 알림 종류와 빈도, 조용한 시간, 미루기를 조정한다. 완료한 일은 반복해서 알리지 않으며, 가족이 공유하는 일에는 담당자와 변경 내역을 표시한다. 아이 생일이나 예정일 변경 시 기존 설정과 새 일정을 비교해 혼란을 줄인다.

웹 알림은 기기·브라우저별 전달 여부를 검증한다. 서비스 안의 알림함을 기본으로 두고, 이메일 안내와 개인 일정표 연결을 보조 수단으로 검토한다. 시간대와 알림 채널 설정을 별도로 관리한다.

수유 알림은 보호자가 정한 계획에 따라 동작한다. 플랫폼이 아이에게 필요한 수유량이나 의료 처치를 자동 처방하지 않는다.

**확정 요구사항(2026-10-13):** 오늘 화면은 마지막 수유뿐 아니라 다음 수유·이유식·식사 시간과 남은 시간을 표시한다. 수유 예상 시간은 마지막 수유 종료 시각과 보호자가 설정한 간격으로 계산한다. 수유·이유식·식사는 하나의 먹이기 흐름으로 묶고 종류로 구분한다. 오늘 화면은 예정 시간만 보여주며 시간 설정은 돌봄 기록에서 한다. 이유식·식사는 하루 여러 시각을 설정한다. 시간 설정은 아이별로 Supabase DB에 저장하고 가족의 기존 아이 접근 권한에 따라 공유·수정한다. 기록이나 설정이 없으면 임의 시간을 만들어 표시하지 않는다.

## 9. 부모 커뮤니티

### 지역과 주제

지역은 시·도와 시·군·구를 기준으로 선택한다. 거주지 외에 관심 지역도 선택할 수 있으며, 정확한 주소를 공개할 필요가 없다. 지역과 주제를 조합해 ‘마포구 + 어린이집’처럼 찾아볼 수 있도록 한다.

주제는 임신·출산, 수유·분유, 수면, 이유식·식사, 건강·예방접종, 어린이집·유치원, 정부 지원, 공동 육아를 기본으로 한다. 초기에는 게시판을 지나치게 잘게 나누지 않고 하나의 글에 지역과 주제 분류를 붙이는 방식을 제안한다.

### 기본 기능과 운영

글·댓글, 사진 첨부, 공감, 저장, 신고, 차단을 제공한다. 운영자는 신고 검토, 게시물 숨김, 이용 제한, 공지 관리를 할 수 있어야 한다. 공개 출시 전에 운영 담당자와 처리 기준을 정한다.

아이의 실명·얼굴·기관·연락처 등 식별 정보가 공개될 수 있는 지점에는 작성 안내와 삭제·신고 수단을 둔다. 의료 관련 게시물은 경험담과 전문 안내를 구분하고, 위험한 권유나 광고는 운영 기준에 따라 처리한다.

한국어와 영어 사용자는 같은 커뮤니티의 글을 볼 수 있다. 서비스의 메뉴와 안내는 두 언어로 제공하되, 사용자 글은 원문을 기본으로 표시한다. 자동 번역은 추후 도입 여부를 결정하고, 도입하면 번역임을 명시한다.

투표 결과는 참여한 사용자들의 의견으로 설명한다. 대표성 있는 조사나 의료 판단의 근거로 표현하지 않는다.

## 11. 한국어·영어와 국가 확장

첫 출시의 한국어·영어 지원 범위에는 가입, 아이 등록, 기록, 일정, 오류, 알림, 도움말, 핵심 안내, 커뮤니티 운영 안내와 투표 문구가 포함된다. 화면의 메뉴만 번역하는 수준으로 끝내지 않는다.

언어와 적용 국가는 분리한다. 한국에 사는 영어 사용자는 영어 화면으로 한국의 절차와 지원 정보를 이용한다. 서비스별로 지원 언어와 제공 상태를 관리하고, 번역 준비가 끝나지 않은 콘텐츠는 준비 중임을 표시한다.

새로운 국가는 해당 국가의 의료 안내, 행정 절차, 지원 제도, 기관 정보, 날짜·단위·시간대와 운영 인력을 준비한 후 출시한다. 한국 기준의 알림을 다른 국가 사용자에게 그대로 제공하지 않는다.

## 12. 외부 서비스 연결과 정보 관리

첫 단계는 플랫폼 안의 기록·준비 목록과 공식 사이트 연결을 중심으로 한다. 병원 예약, 정부 신청, 어린이집 대기 신청을 포둥 안에서 직접 완료하는 기능은 각 기관의 허용 범위와 연동 방식이 확인된 이후 검토한다.

공개 기관 정보 조회와 개인 신청·대기 상태 조회는 별개의 기능이다. 외부 서비스의 계정 비밀번호를 저장하거나, 연동 없이 신청 완료를 보장하지 않는다. 연결이 중단되면 공식 링크와 수동 기록을 제공한다.

제도·건강 콘텐츠에는 출처, 적용 지역, 적용 시점, 마지막 검토일과 검토 담당 정보를 관리한다. 지원금은 ‘받을 수 있는 지원 후보’로 안내하고, 실제 수급 여부는 공식 조건과 기관 판단에 따른다는 점을 해당 안내에 표시한다.

초기 참고할 공식 서비스는 [정부24 행복출산](https://www.gov.kr/mw/AA020InfoCappView.do?CappBizCD=17410000001), [복지로](https://www.bokjiro.go.kr/), [어린이집 정보공개포털](https://info.childcare.go.kr/), [질병관리청 예방접종도우미](https://nip.kdca.go.kr/)다. 출시 전 실제 연결 경로와 콘텐츠를 다시 확인한다.

## 13. 가족 데이터와 건강 정보

아이, 보호자, 가족 관계, 기록, 일정, 할 일, 콘텐츠, 게시물과 투표를 공통 데이터 구조로 관리한다. 서비스를 독립적으로 제공하는 요구가 별도 서버를 여러 개 운영해야 한다는 뜻은 아니다. 초기 운영 규모에 맞는 구조를 선택한다.

보호자 초대에는 접근 범위를 명시하고, 초대 해제와 권한 회수를 제공한다. 가족 기록과 공개 게시물의 공개 범위를 분리한다. 주요 변경에는 작성자와 변경 시각을 남겨 돌봄 인계를 돕는다.

개인정보는 필요한 범위만 수집하고, 초기에는 행정 신청용 식별번호를 받지 않는 방향으로 설계한다. 기록 내보내기와 계정·아이 데이터 삭제 절차, 첨부파일 관리, 접근 통제, 백업과 복구 기준을 공개 전에 준비한다. 보관과 삭제 범위는 실제 운영 정책과 관련 의무를 검토해 확정한다.

건강 기능은 기록과 공식 안내를 제공한다. 관찰한 음식 반응과 진단된 알레르기를 구분하고, 약은 처방된 내용의 기록을 지원한다. 진단이나 약 용량 계산을 제품의 기본 기능으로 넣지 않는다.

## 15. 출시 단계와 완료 조건

### 단계 A — 화면과 이용 흐름 검증

브랜드와 주요 화면 시안을 만들고, 아이 등록부터 첫 기록, 할 일 완료, 가족 공유, 투표 결과 확인까지 검증한다. 예비 부모, 영아 부모, 유아 부모, 영어 사용자를 포함해 사용성 문제를 찾는다. 인터뷰 10~15명과 반복 사용성 확인을 초기 운영안으로 제안한다.

완료 조건은 주요 사용자가 도움 없이 핵심 흐름을 수행하고, 한국어·영어 화면 모두에서 의미와 조작이 전달되는 것이다. 이 단계에서 데이터 구조와 콘텐츠 운영 범위를 확정한다.

### 단계 B — 비공개 시험 운영

아이·가족 프로필, 오늘 화면, 기록, 일정·할 일, 임신·출산·행정 목록, 기본 수유 기록, 병원 일정과 핵심 지원 안내를 구현한다. 커뮤니티와 투표는 운영 도구와 함께 시험한다. 30~50가족을 모집하는 방안을 제안한다.

완료 조건은 기록과 가족 공유의 안정성, 권한 분리, 날짜 변경 처리, 알림 설정, 콘텐츠 검토, 신고 처리, 데이터 삭제를 실제 흐름에서 확인하는 것이다.

### 단계 C — 첫 공개 출시

단계 B의 기능과 지역·주제별 커뮤니티, 매일 투표·결과를 한국어·영어로 공개한다. 모든 서비스 목록은 확인할 수 있도록 하되 출시되지 않은 기능은 준비 중으로 표시한다.

완료 조건은 운영 담당자 확보, 핵심 콘텐츠 검토, 두 언어의 주요 흐름 확인, 주요 모바일·데스크톱 환경 검증, 장애 대응과 문의 경로 준비다. 커뮤니티 운영 준비가 늦어지면 전체 공개 범위를 다시 결정한다.

### 단계 D — 돌봄 기록 확장

수면, 기저귀, 이유식 기본 기록, 성장·발달, 예방접종 안내를 확장한다. 기능 수보다 반복 사용과 기록 편의 개선을 우선한다.

### 단계 E — 기관과 지역 정보 확장

어린이집, 유치원, 취학 준비와 지역별 지원 안내를 확대한다. 기관 데이터 확보와 콘텐츠 유지 역량에 맞춰 지역을 늘린다. 직접 신청·예약이나 개인 이력 연동은 허가와 운영 가능성이 확인된 범위에서 진행한다.

### 단계 F — 국가·언어 확장과 수익화 검토

사용자 유지와 운영 안정성을 확인한 뒤 국가별 서비스를 준비한다. 유료화는 별도 결정 전까지 진행하지 않는다. 구독, 제휴, 기관 대상 서비스는 검토 가능한 선택지이며 확정한 사업 모델이 아니다.

개발 인원, 콘텐츠 검토 인력과 커뮤니티 운영 범위를 정한 뒤 출시 날짜와 예산을 산정한다. 현재 단계에는 특정 출시일을 약속하지 않는다.

기획·개발·디자인 외에 한국어·영어 콘텐츠 관리, 건강 정보 검토, 제도 정보 갱신, 커뮤니티 신고 대응과 사용자 문의 역할이 필요하다. 한 사람이 여러 역할을 맡더라도 공개 전에 책임 범위를 정한다.

## 18. 다음 결정과 개발 준비 산출물

다음에는 첫 공개 출시의 상세 범위를 확정하고, 주요 화면과 이용 흐름을 설계한다. 이어서 서비스별 요구사항과 콘텐츠 목록을 작성하고 개발 규모를 산정한다.

- 첫 공개 출시 기능 목록과 서비스별 한국어·영어 제공 범위.
- 가입, 오늘, 기록, 일정, 가족 공유, 커뮤니티, 투표 화면 설계.
- 아이·가족·기록·할 일·게시물·투표의 데이터와 권한 정의.
- 알림의 생성·변경·완료·미루기 규칙과 날짜 전환 기준.
- 콘텐츠 출처 목록, 검토·번역·갱신 절차와 담당자.
- 커뮤니티 이용 규칙, 신고 처리, 투표 운영과 소규모 집계 기준.
- 개인정보·보관·삭제·가족 초대 정책과 실제 운영 검토.
- 기술 스택, 카카오·네이버·구글 인증 연동·계정 연결 방식, 운영 인력, 예산과 단계별 일정. 소셜 로그인 세 제공자 지원은 확정 요구사항이다.
- 브랜드·도메인·상표 확인과 최종 로고·캐릭터.
- 충분한 사용자 확보의 판단 기준과 이후 수익화 검토 조건.

첫 개발 목표는 부모가 아이를 등록한 뒤, 필요한 준비를 이해하고 기록과 가족 공유를 이어갈 수 있는 경험이다. 이후 기능은 그 경험이 반복 사용으로 이어지는지 확인하면서 확장한다.
